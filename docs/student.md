# Ученик: подбор ёмкости и бейзлайн на CE (шаг 3)

Цель шага — выбрать архитектуру ученика заметно меньше учителя (ResNet-50, 23.7M параметров,
test top1 0.7951) и получить бейзлайн «ученик на CE»: несколько обучений выбранной модели
из разных начальных состояний. С этим бейзлайном на шагах 4–6 сравнивается KD.

Код: `kd/models.py` (`SimpleCNN`), `kd/experiment.py` (серии запусков),
`scripts/capacity_search.py` (сетка), ноутбуки `colab/agent.ipynb`, `colab/train_students.ipynb`.

## 1. Архитектура

`SimpleCNN`:
- 3 стадии по `convs_per_stage` блоков conv3×3 → BN → ReLU;
- ширина стадий `(w, 2w, 4w)`, между стадиями maxpool 2×2 (32 → 16 → 8);
- затем global average pooling и линейный классификатор на 100 классов.

Остаточных связей нет. Ёмкость задают `--cnn_width` (w) и `--cnn_convs_per_stage` (c).

| w \ c | 1 | 2 |
|---|---|---|
| 16 | 30k | 79k |
| 32 | 106k | 300k |
| 48 | 229k | 665k |
| 64 | 397k | 1.17M |

Даже самый большой вариант — 5% параметров учителя.

## 2. Многократное обучение: `Experiment`

`Experiment` (абстрактный класс) принимает класс модели и аргументы её конструктора
и обучает модель `--n_runs` раз из разных начальных состояний (`run(n_runs, init_seed)`).
Подкласс задаёт целевую функцию (`build_objective`) и, для KD на шаге 4, учителя (`teacher`).
Сейчас реализован `CrossEntropyExperiment` — обучение только на метках.

Источники случайности разделены:

| Что | Чем задаётся | Одинаково в запусках серии |
|---|---|---|
| начальные веса запуска `i` | сид `i`-го потомка `SeedSequence(--init_seed)` | нет |
| порядок батчей, аугментации | `--seed` и номер эпохи (`DeviceLoader`) | да |
| прочие операции torch/numpy/random | глобальный `--seed`: выставляется сразу после создания модели | да |
| разбиение train/val | `--split_seed` | да |

Поэтому разброс метрик между запусками серии отражает только начальное состояние.
Сид запуска `i` зависит только от `(init_seed, i)`: серию можно расширить со 100 до 200
запусков, и первые 100 не изменятся. Уже завершённые запуски будут пропущены.

### Параллельное обучение группами: `--parallel_runs K`

Одна модель ученика загружает T4 примерно на треть: обучение упирается в накладные
расходы Python на запуск операций, а не в GPU. При этом все сиды серии известны заранее,
а батчи и аугментации у всех запусков одни и те же. Поэтому K запусков обучаются
синхронно, одной группой (`kd/stacked.py::StackedModel`):
- **Сборка группы.** Каждая модель создаётся под своим сидом, затем параметры и буферы K
  моделей складываются по новой оси (`torch.func.stack_module_state`). Прямой проход
  векторизован (`vmap`): `[B, ...] -> [K, B, C]`, все модели получают один батч.
- **Целевая функция** возвращает лосс каждой модели `[K]`, backward идёт от их суммы.
  Параметры моделей не пересекаются, поэтому каждая получает градиент своего лосса.
  SGD с momentum и weight decay поэлементный, так что один оптимизатор на группу
  эквивалентен K независимым.
- **BatchNorm** обновляет running-статистики каждой модели отдельно.
- **Для KD (шаг 4)** учитель прогоняется один раз на батч для всей группы.

Эквивалентность проверена тестами: K моделей группы совпадают с K отдельными моделями,
а серия группами `[0, 1], [2]` даёт те же метрики и веса, что последовательное обучение,
до 1e-4. Одна оговорка: `GradScaler` AMP общий на группу, и при переполнении fp16
в одной модели шаг пропускают все K. Число пропусков пишется в историю
(`skipped_steps`); ожидается, что это бывает только в начале обучения.

`K` выбирается замером `scripts/bench_parallel.py` на T4: пропускная способность
в моделях·шагах в секунду перестаёт расти, когда GPU насыщен.

### Что сохраняется

После обучения каждая финальная модель замеряется на train (без аугментаций), val и test:
все метрики и компоненты лосса. Всё сохраняется на диск в `<output_dir>/<task_id>/`:
- финальный замер — `run_<i>/final.json`;
- история по эпохам — `run_<i>/history.csv`;
- логиты val/test — `run_<i>/logits.npz`;
- веса — `run_<i>/model_final.pt`;
- сводные таблицы серии — `test_metrics.csv`, `final_metrics.csv`, `history.csv`.

Во время обучения в ClearML идёт только консоль. В конце серии из файлов отправляются
кривые, single values и таблицы-артефакты, главный из них — `test_metrics`. Формат
файлов — `docs/metrics.md`, разделы 3–4.

## 3. Подбор ёмкости: ClearML GridSearch

`scripts/capacity_search.py`:

1. Создаёт базовую задачу-черновик `train.py` через `Task.create`:
   - репозиторий GitHub, ветка `master`, `--arch cnn --n_runs 1 --num_train_epochs 100
     --dataset_name cifar100`;
   - Drive в `--output_dir`;
   - зависимости без torch.
2. Запускает `HyperParameterOptimizer` со стратегией `GridSearch`:
   - сетка `Args/cnn_width` ∈ {16, 32, 48, 64} × `Args/cnn_convs_per_stage` ∈ {1, 2};
   - 8 задач-клонов, каждая модель обучается один раз;
   - цель — последнее значение `top1/val` (финальная модель), максимизация;
   - очередь `colab-t4`, по одной задаче за раз.
3. Собирает таблицу по всем задачам сетки: параметры, `val/top1`, `val/ce`, `val/precision`,
   train top1, время эпохи. Сохраняет её в `out/capacity_search.csv` и артефакт `results`
   задачи-контроллера.

Задачи исполняет `colab/agent.ipynb`, контроллер запускается локально:

```bash
python scripts/capacity_search.py --queue colab-t4
```

Агент берёт код из GitHub, поэтому изменения перед запуском должны быть запушены.

Рецепт у всех конфигураций одинаковый и такой же, как у учителя, кроме числа эпох:
- SGD nesterov, lr 0.1, momentum 0.9, wd 5e-4, батч 128;
- warmup 1 эпоха, затем косинус, без label smoothing;
- **100 эпох**. В KD на каждом шаге ученика нужен прямой проход ResNet-50,
  и 200 эпох на всех запусках шагов 5–6 не помещаются в бюджет Colab.

**Критерий выбора** — только по val, test не используется:
1. отставание от учителя по `val/top1` не меньше 10 п.п.;
2. среди подходящих — модель на участке, где точность ещё растёт с ёмкостью: ученику
   не хватает обучающего сигнала, а не ёмкости, и KD есть что добавить;
3. при равенстве — меньшая модель.

Ожидаемый кандидат — w32/c2 (300k параметров).
